Which model? Ask in order, stop at the first yes

  1. Many similar, simple items (screening, tagging, pulling out fields)? → Haiku 5.5, and validate on a sample.
  2. Everyday reading, writing, analysis or code? → Sonnet 5.5, the default for most research work.
  3. Long, multi-step, many files, or a subtle bug? → Opus 5.5.
  4. Being wrong is very costly (proofs, study design, deep reasoning)? → Fable 5.2.

Not sure? Start with Sonnet. Move up if it struggles, down if it's overkill.

Six prompting patterns

PatternTry this
Say who it's for"Summarise this paper for a PhD student who knows DFT but not machine learning. Five bullets: question, method, data, result, main limitation."
Let it ask first"Before proposing anything, ask me up to 3 questions about my constraints: equipment, time, sample size."

02 · Claude appsProjects, memory, skills

Project instructions template

Prompt
You're helping me write a paper on [topic] for [venue].
Audience: [who reads it].
Notation: follow notation.md exactly.
Style: plain, precise, no hype words ("novel", "groundbreaking").
Never invent citations. If a claim needs one, write [CITE?].
When you're unsure about the science, say so and ask me.

Teach memory a fact

Prompt
Remember: my thesis uses SI units, British spelling, and the symbol κ for thermal conductivity. My advisor prefers short paragraphs.

Review Settings → Memory monthly and delete stale entries. Use an incognito chat for anything you don't want remembered.

Try it · build your first skill (8 min)

Prompt
Use the skill-creator skill to make a skill called "paper-litnote" for me.
I'm a [PhD student in ___] working on [topic].
When I share a paper, it should produce: a one-line takeaway, problem/method/data/result with page refs, limitations, 3 verbatim quotes, and how it relates to my topic.
Ask me 3 questions first to tailor it, then give me the skill as a downloadable zip.

Then upload the zip in Settings → Capabilities → Skills, open a new chat, drop in a PDF and say "notes please". If it doesn't trigger, sharpen the description.

Example SKILL.md

paper-litnote/SKILL.md
---
name: paper-litnote
description: Turn a research paper (PDF, arXiv link) into a structured
  literature note. Use when the user shares a paper and says summarise,
  notes, lit note, or "what does this paper do".
---

2. Problem · Method · Data · Key result (with section/page refs).

02 · Claude appsA literature-review pipeline

1 · You: criteria (scope, years, study types). 2 · Claude: search with a log. 3 · Skill: one lit note per paper. 4 · Claude: compare and find gaps. 5 · You: argue your position. 6 · Claude: check every citation.

Prompt · search log
Keep two separate sections: SEARCH LOG (queries, databases, dates, counts, what you excluded and why) and FINDINGS. Never mix interpretation into the log.
Prompt · compare
From these notes, build a table: paper · method · dataset · metric · result. Then list 3 questions none of them answers, and which paper comes closest to each.
Prompt · step 1, scope
Help me define inclusion criteria for a review on [topic]: years, study types, populations, outcomes. Ask me questions first. Don't propose criteria until I answer.
Prompt · step 3, screening (Haiku 5.5, low effort)
For each abstract: include, exclude or unsure against my criteria, with a one-line reason.
Prompt · step 5, test your argument (Opus 5.5, high)
Here is my argument. Where is it weakest? Which paper in our notes contradicts it?
Prompt · step 6, check citations
Check every reference in this draft: does it exist, are the details right, and does it support the sentence it's attached to? Flag anything you can't verify.

Spot-check 20 of the screening "exclude" decisions yourself before trusting them.

Walkthrough · understand a hard paper

1 · three levels (Sonnet, medium)
Explain this paper at three levels: a final-year undergraduate, a PhD student in my field, and an expert reviewer. One short paragraph each.
2 · equation by equation (Opus, high)
Walk me through equation (7) term by term. What does each symbol mean physically, and what would change if it were zero?
3 · assumptions (Opus, high)
List every assumption the authors make, explicit and implicit. Which one, if false, would break the main result?
4 · figures (Opus, high)
[attach Figure 3] First describe exactly what this figure shows. Then: does it support the claim in Section 4.2? What would a sceptic say?
5 · quiz yourself (Sonnet, medium)
Quiz me with 5 questions to check I really understood this paper. Wait for my answers before giving yours.

Walkthrough · responding to reviewers

1 · triage
Here are the reviews. Make a table: reviewer · comment · major / minor / typo · what they are really asking for. Don't respond yet.

2 · You: mark each row agree · partly · disagree, with one line of reasoning.

3 · draft
Using my decisions, draft a polite, specific response to each comment. Never promise analyses I haven't done. Put [TODO: result] wherever I must add numbers.
4 · stress-test (Opus, high)
Act as Reviewer 2. Read my responses. Which ones don't actually address your concern, and why?

Try it · note it, then attack it (10 min)

Prompt 1
[attach your PDF]
Make a lit note of this paper.
Prompt 2
Now act as a skeptical reviewer for [venue].
List the 5 weakest points in this paper, ranked by severity, each with: the claim, why the evidence is insufficient, and what experiment or analysis would fix it.
Then tell me which of your 5 points you are least sure about.

Writing: edit, don't replace

  • "Here are my bullet points; draft the paragraph, keep every claim, add nothing."
  • Highlight one sentence and ask for a fix in place.
  • "Where would a reader from [other field] get lost?"
  • "Shorten by 30% without losing any number."

02+ · Deep diveClaude Science

A research workbench, not a new model: a desktop app that pairs Claude (the models your plan already has) with an analysis environment on your computer. You get live Python and R kernels, dozens of science databases, your cluster and GPUs, a reviewer agent, and a record of how every output was made. Public beta since 30 Jun 2026. Details checked against the docs on 20 Nov 2026.

Four things people get wrong

MythFact
It's a new science modelAn app. It runs the Claude models in your plan, with the same safeguards. Some sensitive life-science requests may go to a different Claude model.
It's a websiteA local app. The browser tab points at localhost; Windows opens its own window.
"Local" means offline and privateYour files and code stay put. The thinking is remote: whatever Claude reads into the conversation goes to Anthropic.
It's only for biologistsAny field works, but the built-in databases and models are mostly life science. Bring your own skills and connectors.

Rule of thumb: a 40 GB BAM file stays on the cluster; the 200-line summary Claude prints from it does not. Not available in the beta: zero data retention, BAA cover (keep patient data out), inference in your own cloud. Team/Enterprise: no training on your content. Pro/Max: consumer terms, so check your privacy setting. Telemetry has no conversation content; turn it off with disable_telemetry = true in ~/.claude-science/config.toml.

The parts

  • Project: one question or paper. It holds instructions (read at the start of every session), memory, folder grants, and optionally a specialist (a named set of skills, connectors and instructions).
  • Session: one thread, with its own live Python/R kernels (they end after ~30 min idle) and a scratch workspace, cleared ~12 h after the last reply. Fork a session to compare approaches; "Continue as a new session" to carry work over; side chats for quick questions.
  • Plan: for multi-step work Claude proposes a plan; approved steps are tracked. Delegation splits work into parallel tracks.
  • Artifact: any file Claude saves. Every save is a new immutable version with provenance. Comment on part of an artifact and Claude acts on it next turn.
  • Composer shortcuts: @ an artifact or upload · # a past session · / a skill.

The workspace is scratch. If you want it tomorrow, save it as an artifact. Don't move files inside ~/.claude-science by hand.

The sandbox and permission cards

  • Network: deny by default; only package sites, featured databases and hosts you approve, through a local proxy (Settings → Network).
  • Writes: only the session workspace, artifacts and temp. Granted folders are read-only to code; a new folder grant starts on Read-only.
  • Outside the sandbox: only jobs you approve. Cluster and Modal jobs run as you, with everything your account can touch.
  • Approval scopes: Once · This conversation · This project · Global. Review standing grants in Settings → Permissions.

The docs say the sandbox rules "aren't a guarantee". Grant the folder you need, never your whole home directory.

Where to install it

  1. Data fits on your laptop? → the laptop app (macOS 13+, Windows 11, Linux x64).
  2. Data on a lab server or VM you can SSH into? → install it there; open it through an SSH tunnel.
  3. Heavy jobs belong on a Slurm cluster? → add the cluster as an SSH host (nothing is installed there).
  4. Need GPUs or more memory? → connect your own Modal account (billed per second, to you).
  5. Calling one protein model over and over? → register an NVIDIA NIM model endpoint (not in the Windows app).

One cluster job, start to finish

  1. Add the host once: Settings → Compute → SSH hosts. It uses your ~/.ssh/config and key or ssh-agent.
  2. It probes the machine: CPUs, memory, GPUs, CUDA, conda/modules/Apptainer, scratch, Slurm partitions. Edit the host's notes to teach it your conventions ("partition gpu", "module load cuda/12").
  3. Claude proposes a job; a card asks "Run this job on <host>?".
  4. Script and inputs are copied to scratch (must be a shared filesystem) and submitted with sbatch. No Slurm: a detached process. PBS and LSF aren't supported.
  5. It runs outside the sandbox, as you, and survives a dropped connection. Default timeout 30 min.
  6. Outputs come back; files over ~100 MB stay on the cluster with their paths recorded.

Modal: 10 concurrent jobs by default, 12 h container timeout (23 h max), 1 GiB input per submit, 5 GiB outputs. No spend ceiling in the app, and closing the app doesn't stop a running job: set a budget in Modal.

The reviewer and provenance

The reviewer re-reads Claude's recent responses, the approved plan, saved artifacts and the execution record, and flags: results reported as computed when nothing ran · values that contradict their source file · citations that don't support the claim · DOIs that resolve to a different article · approved plan steps not done · conclusions the method doesn't support. It doesn't re-run analyses or judge whether your method was right, and it is the same model family. Automatic on Max, Ultra, Team and Enterprise; on Pro use Request review or turn auto-review on per session. Add field-specific checks in Settings → Specialists → Reviewer.

Reviewer instructions · example
Also flag: any p-value without the test named and n given; any effect reported without a confidence interval; any preprint cited as if peer-reviewed; any figure whose axis labels lack units.

Provenance (artifact menu → Provenance) has five tabs: Messages, Code (download as a script or notebook), Execution Log, Environment (every package and version), Review. If the Code tab and the log disagree, trust the log.

Walkthrough · raw data to a figure you can defend

1 · project instructions (you)
Use R for statistics and Python for figures. Report n, the test and an effect size with every p-value. Colour-blind-safe palettes. Never write into my data folders. Ask before any job longer than an hour.
2 · ask for a plan, not results (you)
Plan an analysis of the counts in ~/data/study: QC, normalisation, differential expression treated vs control, pathway enrichment. Give the method for each step and why. Don't run anything until I approve.
3 · look before you test
Load the counts. Show library sizes and a PCA coloured by batch and by condition. Stop and tell me if batch explains more variance than condition.
4 · bring in the databases
For the top 20 genes, add Ensembl IDs, GTEx tissue expression and any ClinVar pathogenic variants. One table, with the source and access date for every value.
5 · heavy step to the cluster (approve the card "Once")
Run the 10,000-permutation test as a Slurm job on my cluster host. Estimate runtime and memory first.
6 · comment on the figure (select part of it)
Label the top 10 genes, drop the gridlines, Okabe–Ito palette, show n per group.
7 · clear the flags, then attack it
Address every reviewer finding. Then list three ways this result could be an artefact, and test the cheapest one.
8 · leave with methods and a skill
Write the methods paragraph from the execution log and environment, with package versions. Then turn this workflow into a skill called de-analysis.

Not a biologist? The same eight steps work for a simulation sweep or a survey analysis: swap step 4's databases for arXiv, your own MCP connector, or a website you allow.

Science, Code or the app?

  1. Reading, writing or thinking through papers? → the Claude app, in a Project.
  2. Building software: a package, tests, a repo? → Claude Code.
  3. A data analysis where every number must be traceable? → Claude Science.
  4. Science databases, a cluster or GPUs, all in one place? → Claude Science.
  5. Patient data or a clinical decision? → none of them, as-is (no BAA cover; not for clinical use).

Know the edges

  • Confident wrongness survives review: in one hands-on test, a survival result was credited to the wrong variable and the reviewer missed it.
  • No paywalled full text, no reference library, no PRISMA screening or dual review.
  • Built-in connectors and skills skew heavily to life science.
  • Slurm only (no PBS/LSF); Linux servers must be x64 glibc.
  • Workspace cleared ~12 h after the last reply; kernels end after ~30 min idle; projects don't sync between computers.
  • Some biology prompts (e.g. around pathogens) are refused by biosecurity safeguards.
  • Usage counts against your plan's 5-hour and weekly limits, shared with Claude Code and chat; the reviewer uses usage too.

Getting access

  • You: Pro, Max or Ultra: on by default. Download, sign in, no API key.
  • Your lab: the Claude Team plan for scientists. A PI at an academic or nonprofit institute verifies the lab (1–25 seats); Standard seats $0 and Premium $15/month (5× usage) for 12 months, promotional and subject to change. Claude Science is on by default.
  • Your institution: Team or Enterprise. An Owner enables it in Organization settings → Claude Science. HIPAA-enabled orgs: off by default.
  • Also: AI for Science credits for projects; the Life Sciences Verification Program (beta) for approved life-science use cases.

Subagent, or do it yourself?

Subagent: searching many files · an independent review (stats, security) · independent pieces in parallel · keeping your main context clean. Yourself: one tangled bug · a small quick edit · work that needs the whole conversation (use a fork).

Walkthrough · notebook → reproducible pipeline

1 · plan (Opus, high, plan mode)
Read explore.ipynb. Propose a script layout: config, data loading, analysis, plots, with a command-line entry point. Don't write code yet.
2 · baseline
Before refactoring, run the notebook end to end and save every output number to baseline.json.
3 · implement (Sonnet, medium)
Implement the plan. Pin package versions in requirements.txt. Every random operation takes its seed from config.yaml.
4 · diff
Run the new pipeline and diff every number against baseline.json. Report any difference above 1e-6 and explain it.
5 · lock it in
Add a test that reproduces Figure 2's numbers, and a hook that runs the tests after every edit.

03 · Claude CodeHooks, MCP and plugins

A hook is code that runs on an event, every time. Easiest way to add one: ask Claude, e.g. "Add a hook that runs the tests after every edit."

.claude/settings.json (simplified)
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "pytest -q -x" }]
    }],
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": "scripts/guard_raw_data.sh" }]
    }]
  }
}

The tool call arrives as JSON on stdin; exit code 2 from a PreToolUse hook blocks the action and tells Claude why.

Cost levers: cache the shared prefix (instructions, codebook) · Batch API for bulk (50% off, results within 24 h) · the smallest model that agrees with a bigger one on 50 hand-labelled items.

Pattern: codebook → cache → batch → Haiku + JSON schema → hand-check a random 5% → report agreement (e.g. Cohen's κ) in your methods.

Checklist · before you run 10,000 calls

Ask yourselfIf yes
More than ~100 items, results can wait up to 24 h?Batch API (50% off)
The same long instructions or codebook in every call?prompt caching
A simple, repetitive judgement?Haiku 5.5 at low effort
You need specific fields back?a JSON schema (output_config.format)
Will the results go in a paper?pin the model ID, log prompts, hand-check a sample, report agreement

Run 20 items first and read every output before launching the full batch.
