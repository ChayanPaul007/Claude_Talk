00 · OpeningModels and effort

Which model? Ask in order, stop at the first yes

  1. Many similar, simple items (screening, tagging, pulling out fields)? → Haiku 5.5, and validate on a sample.
  2. Everyday reading, writing, analysis or code? → Sonnet 5.5, the default for most research work.
  3. Long, multi-step, many files, or a subtle bug? → Opus 5.5.
  4. Being wrong is very costly (proofs, study design, deep reasoning)? → Fable 5.2.

Not sure? Start with Sonnet. Move up if it struggles, down if it's overkill.

Six prompting patterns

PatternTry this
Say who it's for"Summarise this paper for a PhD student who knows DFT but not machine learning. Five bullets: question, method, data, result, main limitation."
Let it ask first"Before proposing anything, ask me up to 3 questions about my constraints: equipment, time, sample size."
Separate evidence from opinion"For each claim, quote the supporting sentence with its page. Mark your own inferences as MY READING."
Ask for its uncertainty"Give a confidence (high / medium / low) for each conclusion, and tell me which one you're least sure about."
Show the output shape"One row per paper: title | n | method | metric | result. Write 'not stated' if missing. Never guess."
Make it argue back"Argue against my hypothesis as a hostile reviewer would. Which objection is strongest, and what data would answer it?"

02 · Claude appsProjects, memory, skills

Project instructions template

Prompt
You're helping me write a paper on [topic] for [venue].
Audience: [who reads it].
Notation: follow notation.md exactly.
Style: plain, precise, no hype words ("novel", "groundbreaking").
Never invent citations. If a claim needs one, write [CITE?].
When you're unsure about the science, say so and ask me.

Teach memory a fact

Prompt
Remember: my thesis uses SI units, British spelling, and the symbol κ for thermal conductivity. My advisor prefers short paragraphs.

Review Settings → Memory monthly and delete stale entries. Use an incognito chat for anything you don't want remembered.

Try it · build your first skill (8 min)

Prompt
Use the skill-creator skill to make a skill called "paper-litnote" for me.
I'm a [PhD student in ___] working on [topic].
When I share a paper, it should produce: a one-line takeaway, problem/method/data/result with page refs, limitations, 3 verbatim quotes, and how it relates to my topic.
Ask me 3 questions first to tailor it, then give me the skill as a downloadable zip.

Then upload the zip in Settings → Capabilities → Skills, open a new chat, drop in a PDF and say "notes please". If it doesn't trigger, sharpen the description.

Example SKILL.md

paper-litnote/SKILL.md
---
name: paper-litnote
description: Turn a research paper (PDF, arXiv link) into a structured
  literature note. Use when the user shares a paper and says summarise,
  notes, lit note, or "what does this paper do".
---
# Literature note
1. One-line takeaway (≤ 25 words).
2. Problem · Method · Data · Key result (with section/page refs).
3. Assumptions and limits the authors admit.
4. Limits they don't admit (mark as MY READING).
5. 3 quotes worth keeping, verbatim, with page.
6. How it relates to: {{my thesis topic}}.
Never fill gaps from memory; write "not stated".

02 · Claude appsA literature-review pipeline

1 · You: criteria (scope, years, study types). 2 · Claude: search with a log. 3 · Skill: one lit note per paper. 4 · Claude: compare and find gaps. 5 · You: argue your position. 6 · Claude: check every citation.

Prompt · search log
Keep two separate sections: SEARCH LOG (queries, databases, dates, counts, what you excluded and why) and FINDINGS. Never mix interpretation into the log.
Prompt · compare
From these notes, build a table: paper · method · dataset · metric · result. Then list 3 questions none of them answers, and which paper comes closest to each.
Prompt · step 1, scope
Help me define inclusion criteria for a review on [topic]: years, study types, populations, outcomes. Ask me questions first. Don't propose criteria until I answer.
Prompt · step 3, screening (Haiku 5.5, low effort)
For each abstract: include, exclude or unsure against my criteria, with a one-line reason.
Prompt · step 5, test your argument (Opus 5.5, high)
Here is my argument. Where is it weakest? Which paper in our notes contradicts it?
Prompt · step 6, check citations
Check every reference in this draft: does it exist, are the details right, and does it support the sentence it's attached to? Flag anything you can't verify.

Spot-check 20 of the screening "exclude" decisions yourself before trusting them.

Walkthrough · understand a hard paper

1 · three levels (Sonnet, medium)
Explain this paper at three levels: a final-year undergraduate, a PhD student in my field, and an expert reviewer. One short paragraph each.
2 · equation by equation (Opus, high)
Walk me through equation (7) term by term. What does each symbol mean physically, and what would change if it were zero?
3 · assumptions (Opus, high)
List every assumption the authors make, explicit and implicit. Which one, if false, would break the main result?
4 · figures (Opus, high)
[attach Figure 3] First describe exactly what this figure shows. Then: does it support the claim in Section 4.2? What would a sceptic say?
5 · quiz yourself (Sonnet, medium)
Quiz me with 5 questions to check I really understood this paper. Wait for my answers before giving yours.

Walkthrough · responding to reviewers

1 · triage
Here are the reviews. Make a table: reviewer · comment · major / minor / typo · what they are really asking for. Don't respond yet.

2 · You: mark each row agree · partly · disagree, with one line of reasoning.

3 · draft
Using my decisions, draft a polite, specific response to each comment. Never promise analyses I haven't done. Put [TODO: result] wherever I must add numbers.
4 · stress-test (Opus, high)
Act as Reviewer 2. Read my responses. Which ones don't actually address your concern, and why?

Try it · note it, then attack it (10 min)

Prompt 1
[attach your PDF]
Make a lit note of this paper.
Prompt 2
Now act as a skeptical reviewer for [venue].
List the 5 weakest points in this paper, ranked by severity, each with: the claim, why the evidence is insufficient, and what experiment or analysis would fix it.
Then tell me which of your 5 points you are least sure about.

Writing: edit, don't replace

  • "Here are my bullet points; draft the paragraph, keep every claim, add nothing."
  • Highlight one sentence and ask for a fix in place.
  • "Where would a reader from [other field] get lost?"
  • "Shorten by 30% without losing any number."

App or Claude Code?

If it runs something or changes a file on your machine, use Claude Code (terminal, desktop Code tab or IDE). Reading and writing text and PDFs → the app. A paper plus its analysis code → Code in the repo, a Project for the writing.

Plan first, or just do it?

Plan first (Shift+Tab) whenJust do it when
more than one file will changea one-line fix you can describe exactly
you don't know the codebase yetrenaming, formatting, a typo
it's hard to undo: data, configs, cluster jobsit's small and easy to revert with git

Subagent, or do it yourself?

Subagent: searching many files · an independent review (stats, security) · independent pieces in parallel · keeping your main context clean. Yourself: one tangled bug · a small quick edit · work that needs the whole conversation (use a fork).

Walkthrough · notebook → reproducible pipeline

1 · plan (Opus, high, plan mode)
Read explore.ipynb. Propose a script layout: config, data loading, analysis, plots, with a command-line entry point. Don't write code yet.
2 · baseline
Before refactoring, run the notebook end to end and save every output number to baseline.json.
3 · implement (Sonnet, medium)
Implement the plan. Pin package versions in requirements.txt. Every random operation takes its seed from config.yaml.
4 · diff
Run the new pipeline and diff every number against baseline.json. Report any difference above 1e-6 and explain it.
5 · lock it in
Add a test that reproduces Figure 2's numbers, and a hook that runs the tests after every edit.

Example CLAUDE.md

CLAUDE.md
# Project: cryo-EM particle analysis
## Run
- env: `conda activate cryo` (env.yml)
- tests: `pytest -q` (must pass before commit)
- full pipeline: `make figures` (~20 min, GPU)
## Rules
- data/raw/ is READ-ONLY. Never modify or move.
- Every random op takes `seed` from config.yaml.
- Plots: use style/lab.mplstyle, SI units.
- New analysis = new script in analysis/, not a notebook.
## Gotchas
- loader.py assumes float32; MRC files are float16.
- Cluster jobs: see @docs/slurm.md

Diagnose before you change

Prompt
The fit in fit_spectra.py gives negative widths on ~3% of samples. Find out why. Don't fix yet.

Refactoring science code: diff every number

Prompt
Before changing anything: run the current pipeline on data/sample and save outputs to /tmp/before. After your change, run it again and diff every number. Report any difference above 1e-6.

Prompt (in plan mode)
Explore this repo and tell me:
1) how to run it end to end,
2) the 3 riskiest places for a silent numerical bug,
3) what's untested.
Then propose a plan to add one regression test for the most important result. Don't write code yet.

03 · Claude CodeHooks, MCP and plugins

A hook is code that runs on an event, every time. Easiest way to add one: ask Claude, e.g. "Add a hook that runs the tests after every edit."

.claude/settings.json (simplified)
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "pytest -q -x" }]
    }],
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command", "command": "scripts/guard_raw_data.sh" }]
    }]
  }
}

The tool call arrives as JSON on stdin; exit code 2 from a PreToolUse hook blocks the action and tells Claude why.

MCP servers
# a remote server (HTTP)

05 · API & Agent SDKStructured extraction at scale

extract.py
import anthropic, json
client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY

schema = {"type": "object", "additionalProperties": False,
  "properties": {"organism": {"type": ["string", "null"]},
                 "sample_size": {"type": ["integer", "null"]},
                 "method": {"type": "string", "enum": ["in vivo", "in vitro", "in silico"]}},
  "required": ["organism", "sample_size", "method"]}

msg = client.messages.create(
    model="claude-haiku-5-5", max_tokens=1024,
    system="Extract study facts. Use null if not stated.",
    messages=[{"role": "user", "content": abstract}],
    output_config={"format": {"type": "json_schema", "schema": schema}},
)
row = json.loads(next(b.text for b in msg.content if b.type == "text"))

Cost levers: cache the shared prefix (instructions, codebook) · Batch API for bulk (50% off, results within 24 h) · the smallest model that agrees with a bigger one on 50 hand-labelled items.

Pattern: codebook → cache → batch → Haiku + JSON schema → hand-check a random 5% → report agreement (e.g. Cohen's κ) in your methods.

Checklist · before you run 10,000 calls

Ask yourselfIf yes
More than ~100 items, results can wait up to 24 h?Batch API (50% off)
The same long instructions or codebook in every call?prompt caching
A simple, repetitive judgement?Haiku 5.5 at low effort
You need specific fields back?a JSON schema (output_config.format)
Will the results go in a paper?pin the model ID, log prompts, hand-check a sample, report agreement

Run 20 items first and read every output before launching the full batch.

06 · Research integrityFailure → habit

FailureHabit
Invented references[CITE?] placeholders; verify every reference against its DOI
Confident wrong mathsmake it compute in code, not prose; ask what it's least sure of
Silent edits to dataraw data read-only via deny rules or hooks; git everything
It agrees with youdon't reveal your answer first; ask it to argue the other side
Hidden instructions in PDFs/pagesreview actions before approving them
Confidential materialno unpublished third-party data or manuscripts under review
